# AFI Resolve 2.0 — Project Status & Gap Analysis

Audit date: **10 November 2026, Asia/Singapore**. Audit only; no application fixes, deployments, pushes, infrastructure changes or real emails were performed.

## 1. Executive summary

**The complete Customer Portal → RM → correction → Operations demonstration is not ready.** There are two substantial frontend implementations, but the Customer Portal targets customer APIs that are absent from the reviewed Spring Boot application. The staff document workflow works with explicitly labelled template fallback. Live Gemini works for some PDFs, but the live workflow encountered a supporting-document verification failure that blocked autonomous attachment.

The principal findings are:

1. **Customer integration is broken against the current backend.** The portal requires Bearer sessions and /api/customer/* routes; Spring currently supplies staff Basic authentication and /api/documents/* routes. Customer provisioning, customer ownership mappings, customer-safe response DTOs, upload request replay and customer notification persistence are absent from this backend.
2. **A real staff API workflow passed in isolation:** three PDFs → validation → verified automatic supporting attachment → two correction tasks → corrected PDF replacement → automatic revalidation → **20/20 checks passed**, zero open tasks and one Operations routing record. Every extraction/investigation in this successful run was **DETERMINISTIC_FALLBACK**, not Gemini.
3. **Live Gemini is partially working, not reliably demo-ready.** A real tax PDF extracted successfully using Gemini. In a separate complete live intake, the three incoming forms and investigation used Gemini, but the seeded repository source was ineligible: automatic attachment was BLOCKED and explicit resolution returned NO_AUTHORISED_SOURCE. A direct live extraction of that supporting PDF reproduced UNVERIFIED_OUTPUT, producing fallback with requires_review=true.
4. **Real SMTP is not implemented.** The portal contains simulated-email presentation, but there is no mail transport or customer notification service in the reviewed backend. An inbox label is not evidence of a sent or even persisted email.
5. **Deployment is preparation, not verified infrastructure.** AWS Compose, an RDS profile, an S3 adapter and Nginx configuration exist. Cloud runtime, RDS TLS, S3 permissions, public HTTPS and Vercel publication were not verified. Required AWS settings and the local RDS CA bundle are absent. The current private local .env also fails Compose parsing.
6. Both frontend production builds passed. Eight focused Java tests and both sets of three frontend tests passed. The selected AI checks produced **52 passes and one failure**. Limited real Chrome checks passed for RM login/navigation and the portal's unauthenticated page; this does not establish authenticated portal functionality.

## 4. Partially implemented or unverified features

### Customer Portal and backend contract

The portal has genuine API client code rather than successful hardcoded responses. Its authentication, uploads and records nevertheless cannot operate against this backend. Changing only VITE_API_BASE_URL will not resolve the incompatibility.

| Contract item | Customer Portal expects | Current backend provides |
| --- | --- | --- |
| Authentication | POST /api/customer/auth/token; Bearer token; GET /me; POST /auth/logout | Staff GET /api/auth/me with Basic auth; no customer tokens/revocation |
| Provisioning and ownership | Customer identity bound server-side to customer reference and assigned RM | Staff in-memory users; submissions contain owner_name and customer_reference; no customer identity mapping |
| New intake | Multipart POST /api/customer/submissions, returning customer-safe Detail | JSON POST /api/documents/submissions, then separate multipart POST /submissions/{id}/upload |
| Add/replace documents | /submissions/{id}/documents and /documents/{docId}/replacement | /api/documents/submissions/{id}/upload with optional replace query parameter |
| Mutation replay | Idempotency-Key plus identical ordered file fingerprints | Document resolution has idempotency; intake/upload do not implement the portal's replay contract |
| Responses | camelCase submission timestamps, caseReference, simplified documents and corrections | Staff-oriented database-style fields, checks, exceptions, tasks, investigations, audit and simulations |
| Notifications | GET /api/customer/notifications with customer-scoped records | No customer notification endpoint/table/service |
| CORS | Portal origins and Authorization/Idempotency-Key allowed | One afi.cors-origin; allowed headers only Authorization and Content-Type |
| RM attribution | Customer Portal source filter / incoming customer cases | No source/customer_id fields in migrations; no corresponding source filter in RM queue |

Evidence: CP:src/auth.tsx:29, src/lib/api.ts:3–11 and :55–56, src/types.ts, src/components/Upload.tsx:76–81, src/pages/SubmissionDetail.tsx:18; RM:DocumentController.java:21–66, SecurityConfig.java:24–57 and :82–89; database migrations V2 and V3.

The portal retains tokens only in memory and scopes upload retry metadata by customer/API. Those client precautions are implemented and its pure retry helpers passed tests. They cannot substitute for server authentication, ownership enforcement or durable idempotency. Refresh requires re-login by design. No registration/password recovery feature is supplied; these are outside the demonstrated account-provisioning design.

### PDF extraction and AI

- The service parses actual PDF bytes with pypdf, then sends numbered extracted text to Gemini. It does not send a rendered PDF for visual analysis and does not OCR scanned pages.
- Supported input is explicitly synthetic, text-readable PDF: up to 10 MB and 30 pages, bounded page text and four recognised form families. Arbitrary real customer/bank forms are intentionally rejected. Signature indicators are test fields, not authenticated signatures.
- Structured schemas, closed field names, page citations, source-label matching and advisory-only actions are implemented. Selected tests exercise fabricated citations, wrong-field evidence, missing markers and provider/schema failures. These mocked cases are not an accuracy benchmark.
- Fallback is restricted to original labelled templates with unambiguous classification. With no key, flexible layouts fail AI_NOT_CONFIGURED. Provider errors on flexible layouts fail AI_SERVICE_ERROR; ungrounded output fails EXTRACTION_FAILED. Template fallback is explicitly labelled and can require review after schema/source failures.
- Cross-document violations are decided by Spring's approved deterministic rules. Gemini extracts/advises; it does not independently authorise a correction or declare banking-policy compliance.
- Live status is in-memory process telemetry. A configured key or health=UP does not prove the next extraction will succeed. No sustained reliability, varied-layout precision/recall, provider outage load or concurrent-throughput benchmark was performed.

References: RM:ai-service/app/documents.py:193–278; document_intelligence.py:20–74 and :118–147; backend/DocumentService.java:466–530 and :734–827.

### Autonomous resolution and handover

The implemented autonomous action is **ATTACH_VERIFIED_DOCUMENT**. The orchestrator is invoked synchronously inside transactional upload/validation; it is independent of an open browser, but is not a continuously polling document worker. Candidates must match the case reference, authorisation, type, expiry and extraction certainty. Preflight predicts effects; execution verifies storage hash/size and persisted outcome. Attempts are bounded and keyed to an evidence snapshot. Fallback success is real administrative execution over test records, not fabricated UI animation.

Repository population is currently synthetic demo setup (DocumentService.java:1486). There is no real supporting-document search connector. With AWS demo disabled, ordinary case creation does not seed an authorised source. Fields such as dates, signatures and conflicting addresses require corrected customer PDFs. Routing means internal status/history persistence; no external Operations system receives a message.

References: RM:DocumentOrchestrator.java:37–199; DocumentService.java:1019–1202, :1206–1369; PolicyService.java:11–49.

## 6. AWS, Vercel and SMTP readiness

### AWS

**Prepared:** three service Dockerfiles; health checks; non-root backend/AI containers; private inter-service network; AWS Compose overrides that remove the local database dependency/mount; RDS JDBC verify-full TLS URL and read-only CA mount; an EC2-instance-role-only S3 adapter using conditional writes, private reads, AES256 server-side encryption and rollback deletion; Nginx upload limits and API proxying. The AWS profile requires supplied credentials and disables demo controls by default.

**Not verified or missing:**

- No AWS/EC2 account session, host access or usable deployment credentials were available in this audit. AWS CLI and Docker Engine CLI were absent. A standalone Compose parser was available; parsing is not a container runtime test.
- No evidence was obtained for EC2 instance state, security groups, IAM attachment/IMDSv2 reachability, actual bucket policy, RDS existence/connectivity/certificates, backups or cloud monitoring. Resource names in files do not prove provisioning.
- RDS_HOST, DB_USERNAME, DB_PASSWORD, AWS application/service credentials, AWS_FRONTEND_ORIGIN and S3_BUCKET were absent from the inspected local environment/private configuration. The RDS CA mount source does not exist locally.
- AWS Nginx listens only on **80**, and Compose publishes only port 80. There is no enabled HTTPS listener, certificate/renewal setup or ALB/ACM infrastructure definition. HTTPS alternatives are documentation, not provisioned resources.
- The portal explicitly refuses non-loopback HTTP API URLs. A public HTTP-only AWS deployment cannot satisfy its production API configuration.
- No Terraform/CloudFormation/CDK provisioning definitions or executed migration were found. Selecting S3 does not copy existing local PDFs or move the database. Existing version storage keys must be preserved and verified during migration.
- Demo source/sample controls require both the demo flag and demo/test profile. For an AWS synthetic demo, the documented opt-in needs both AWS_DEMO_ENABLED=true and AWS_EXTRA_PROFILES=,demo; default AWS mode supplies no demo repository seed.

References: RM:docker-compose.aws.yml; backend/src/main/resources/application-aws.yml; S3DocumentStorage.java; frontend/nginx.aws.conf; infrastructure/aws/s3-policy.json and README.md. The committed IAM JSON is a role-permission example, not proof of the attached policy or bucket restrictions.

### Vercel

CP:vercel.json provides a valid-looking Vite/dist build definition, SPA fallback and security headers; local production build passed. CP:.env.example supplies a **public build-time** VITE_API_BASE_URL ending in /api/customer. There is no Vite proxy. Production requires a real HTTPS customer API and exact backend allowlisting of the deployed Vercel/custom-domain origin, plus Authorization and Idempotency-Key preflight support. The manifest does not implement an API or provide authentication. No live Vercel URL, deployment logs, environment values, custom domain or production deep-link test was available. RM frontend has Docker/Nginx deployment, not its own Vercel configuration.

### SMTP

**Real delivery: Not Implemented.** RM backend/pom.xml has no Spring mail dependency; application YAML and Compose have no SMTP settings; no Java/Python sender, template delivery service, notification outbox or email worker exists. Document submissions also have no dedicated verified recipient identity/email field. Extracted contact_information is untrusted PDF content and should not automatically determine a delivery recipient.

CP Notification types include channel/deliveryStatus; Records.tsx recognises SIMULATED and Notifications.tsx labels email simulated. Those are display capabilities. The current backend has no corresponding persisted customer notifications or simulation sender. RM:frontend/src/pages/Settings.tsx:299 explicitly says no email/SMS is configured.

To demonstrate real email later, provision a verified synthetic customer's controlled test recipient, configure a real SMTP transport/secret, persist a post-commit notification/outbox, send with bounded retry/idempotency, and record accepted/failed delivery accurately. Provider acceptance is not proof of inbox delivery. Credentials, recipient ownership, sender verification and an authorised test inbox are dependencies. **No email was sent during this audit.**

## 9. Recommended implementation order

1. **Reconcile the actual backend baseline** with the Customer Portal contract and preserve current local work. Locate the missing customer backend before duplicating it. Resolve private environment syntax and the intended local database connection (A1, A5, B8).

3. **Stabilise bundled live Gemini inputs**, especially the repository supporting document. Keep the verified template fallback as a clearly disclosed contingency. Repair failed/stale tests (A4, B1).
4. **Make customer corrections and both UIs agree** on one case/revision, with accurate review/Operations semantics and refresh behaviour (B6), then add the real notification/outbox/SMTP path using a controlled recipient (A6).
5. **Complete the deployment inputs and HTTPS/CORS configuration**, image checks, migration/backup and exact release preparation (A3, A7, B3, B5, B7). Environment preparation can proceed alongside application work; deployment still requires later authorisation.
6. **Verify the complete current-source two-app workflow**, first locally, then on the authorised hosted environment with genuine provider/email evidence. Capture strict-live and fallback outcomes separately (A8).
7. Address measured query/performance issues and remaining mobile/presentation polish after the critical journey passes (B9, C1–C3).
